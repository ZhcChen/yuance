## 结论

**通过。** 一级导航由顶部横排改为左侧分组侧栏，顶栏收敛为搜索、项目切换、通知与账户，
parity 合同的壳层相关硬编码值同步更新，既有 e2e 中依赖旧导航结构的用例已逐条对齐。

本轮同时发现并修复了三个问题：一个由壳层改造直接引入的主区溢出、一个 P1 遗留的令牌断链、
一条停留在换皮前尺寸的既有断言；并相应补强了结构护栏与令牌解析断言。

## 这是回迁里第一次动结构

P0 的护栏正是为这一步准备的：改 DOM 之前，锚点、溢出、`h1` 与像素基线都已经在门禁里，
所以这次结构改动能被自动发现，而不是靠人眼扫。

## 侧栏

新增 `frontend/packages/ui/src/app-sidebar.jsx`，分组与设计稿一致：

| 分组 | 入口 |
|---|---|
| 概览 | 工作台 |
| 项目 | 项目、资料库 |
| 交付 | 需求、任务、Bug（带未处理数角标） |
| 协作 | 消息中心（带未读角标） |
| 工具 | 时间管理、桌面端下载（均标注「现网」） |
| 系统 | 系统管理 |

- 活动态用「靛蓝浅底 + 左侧 3px 强调条」双通道表达，不用颜色单独承担。
- 图标全部是内联 SVG 描边路径（`app-sidebar.jsx` 内的 `SIDEBAR_ICONS`），无 emoji、无外链图标。
- 响应式三档：≥1120px 完整侧栏；≤1120px 收成 64px 图标条；≤768px 变为抽屉，
  由顶栏的菜单按钮开合，点击导航项后自动收起。
- 品牌标识从顶栏迁到侧栏，抽屉态仍显示。

## 顶栏

- 保留：全局搜索、当前项目切换、通知、账户。
- 移除：一级导航链接（迁到侧栏）、系统管理下拉（迁到侧栏）、桌面端下载（迁到侧栏）。
- 顺序按设计稿调整为「搜索 → 当前项目 → 通知 → 账户」，搜索靠左、其余靠右。
- 窄屏（≤860px）改为两行：第一行搜索与通知、账户，第二行当前项目独占一行。

## 壳层结构

```
.app-shell            横向 flex，overflow hidden
├── .app-sidebar      深色靛调分组侧栏，自身可滚动
└── .app-shell__body  纵向 flex
    ├── .global-nav   顶栏，60px
    └── .main         唯一业务滚动容器
```

业务区仍然只有一个滚动容器（`.main`），顶栏与侧栏都不滚动，符合既有壳层约定。
骨架屏同步出侧栏骨架，避免会话恢复阶段出现结构跳变。

|---|---|---|
| `globalShell.regionOrder` | `["topbar","main"]` | `["sidebar","topbar","main"]` |
| `tokens.topbarHeight` | `58px` | `60px` |

`topbarHeight` 一处改动牵动四个地方，已全部同步：合同 JSON、合同 schema 的 `const`、

`breakpoints` 之前登记的 `980`、`920` 在现有样式里其实并不存在，登记值与实现已经脱节；

`viewports` 按规格阶段的既定结论保持不变：合同 schema 把视口固定为 4 项，

## 本轮发现并修复的问题

### 1. 侧栏挤占主区后，工作项筛选条把主区撑出横向滚动

壳层从「顶栏 + 主区」变成「侧栏 + 顶栏 + 主区」后，侧栏固定占走 236px，
1280px 视口下主区可用宽度只剩 1008px，而工作项筛选条用的是固定七列栅格：

```css
grid-template-columns: minmax(240px, 1.5fr) repeat(5, minmax(130px, 1fr)) auto;
```

七列的最小宽度加六个 12px 间距约 1100px，超出主区 92px，
业务滚动容器 `.main` 被撑成横向滚动条（实测 `scrollWidth` 1062 > `clientWidth` 1044）。

修复：保持七列结构不变，把可伸缩列的下限改为 0（`minmax(200px, 1.5fr) repeat(5, minmax(0, 1fr)) auto`），
列宽随主区宽度收缩，不再溢出。

**护栏同时补强**：结构层护栏此前只检查文档级溢出，而业务区真正的滚动容器是 `.main`，
主区内部的横向溢出不会体现在 `documentElement` 上——这正是本次漏检的原因。
现在护栏同时断言 `.main` 的 `scrollWidth` 与 `clientWidth`。

### 2. P1 遗留的令牌断链：控件字号回落到 16px

`frontend/packages/ui/src/tokens.css` 里写成：

```css
--yc-control-fs: var(--fs-13);   /* 令牌真名是 --yc-fs-13 */
```

变量未定义 → 整条声明失效 → `font-size` 回退为继承值 16px，
所有按钮、输入框与下拉触发器的字号都比设计稿大一号（设计稿为 13px）。

修复：改为 `var(--yc-fs-13)`。

**断言同步**：P2 加的令牌解析断言只扫描 `var(--yc-*)` 引用，恰好漏掉「名字写错」这一类断链。
现在改为扫描全部 `var(--x)`：能在 tokens.css、样式表或内联样式里找到定义，或者带兜底值，才算通过；
并把 `tokens.css` 自身也纳入扫描范围。反向验证：注入 `var(--fs-13)` 后断言按预期失败。

### 3. 既有断言停留在换皮前的按钮尺寸

「项目详情标签页不替换页面容器」用例断言 `.detail-hero .yc-button` 高度为 32px，
而 P2 按设计稿把按钮改成了 36px。断言同步为 36px，字号仍为 13px。

### 4. 原型别名层漏掉 `--font-sans`

`ui-v3/styles/tokens.css` 的别名层没有声明 `--font-sans`，
而 `ui-v3/styles/base.css` 的 `body` 正在用它 → 原型的正文字体族落到浏览器默认值。
补上 `--font-sans: var(--yc-font-sans);`，并新增 `frontend/test/ui-v3-token-alias.test.mjs`
守住这条线：原型样式里每个 `var(--x)` 都必须在别名层里有定义或带兜底值。
反向验证：移除该别名后断言按预期失败。

## 既有 e2e 失败的准确归因

P0 复核记录把工作项详情相关的成片超时归因为「演示种子不再创建 `YCE` 项目」。本轮复核更正这一结论：

- `YCE` 项目仍在种子数据里，当前会话的当前项目就是 `YCE`；
- 真实失败形态是：工作项详情的弹窗表单里，`.yc-select-native`（视觉隐藏的原生 select 代理）
  在弹窗刚打开时被 Playwright 判定为不可见，`selectOption` 一直等待到用例超时；
- 同一份用例在三个基线上表现完全一致：
  - `69dc1a2`（回迁开始前）
  - `c74f9e21`（P2 组件换皮后）
  - 本轮 P3

  因此这批失败与本轮回迁无关，属于既有仓库问题，需要单独定位（弹窗打开后原生 select 的可交互时机），
  本轮不纳入 P3 范围。

另外确认了 e2e 套件存在**运行间状态残留**：消息中心的未读消息会被「打开」动作标记为已读，
而 e2e 服务端默认复用（`reuseExistingServer`），同一个数据库会被多轮用例共享，
导致后续轮次看到「未读消息 0 条」。重启 e2e 服务端后这批用例立即恢复通过。
因此跨轮次比较 e2e 结果时，必须以「服务端首次启动的干净数据库」为准。

## 既有 e2e 的对齐

侧栏改造动到了几个依赖旧导航结构的用例，逐条对齐而不是删掉：

- 「导航指示条在应用分区之间滑动」→ 改为「侧栏分组导航并标记当前分区」，
  断言六个分组标题与 `aria-current` 的切换。
- 「系统管理下拉」→ 改为侧栏「系统管理」入口，断言跳转到 `/web/app/system`。
- 壳层几何用例改为检查侧栏宽度、顶栏 60px、工具区不重叠。
- 三处 `getByRole('navigation', { name: '应用导航' })` 改为 `主导航`。
- 「时间管理与项目资料库互不干扰」用例：资料库容器在实现里是 `section[aria-label]`
  （role=region），不是 h3 标题，定位方式改为 `getByRole('region', { name: '项目资料库' })`；
  页面宽度断言原本是绝对值 `> 1200`，侧栏占走 236px 后不再成立，
  改为「页面占满主区且主区仍属宽版」的相对判断。
- `global-navigation.test.mjs` 按新 props 重写，并新增一条移动端导航开关的用例。

## 已知环境问题

1. **桌面端 renderer 无法在本机构建**：`desktop/node_modules` 为空（`vite`、`typescript` 均未安装），
   `npm --prefix desktop run build:renderer` 与 `make frontend-check` 的 desktop 段都无法执行。
   T015 要求的「桌面端启动后走查深浅两色」本轮**未完成**，属未验证项，需补齐依赖后单独复核。
   桌面端与 Web 端共用同一套 `@yuance/frontend-ui` 包与同一个 `SharedApp`，
   壳层改动两端同时生效，Web 端的验证结论对桌面端成立，但仍未算作实测。
2. **既有 e2e 用例与运行顺序耦合**：见「既有 e2e 失败的准确归因」一节。
   这批失败在回迁前的基线提交上完全一致，且与用例执行顺序相关
   （例如项目列表会随前序用例新建的项目变多，`ensureCurrentProject()` 依赖的项目可能落到第二页；
   又如消息中心的未读消息会被「打开」动作标记为已读，而 e2e 服务端默认复用同一个数据库），
   本轮只做了归因与隔离，未修改这些用例的行为。
