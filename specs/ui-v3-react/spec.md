# 元策 UI v3 回迁 React 生产实现

状态：草稿
来源：`ui-v3/` 设计原型（2026-11 评审定稿石墨蓝色系）、`specs/ui-v3/spec.md`、`frontend/parity/` 视觉合同与体验清单

## 目标与范围

把 `ui-v3/` 原型确立的视觉与交互设计，回迁到生产实现（`frontend/packages/ui` + `frontend/packages/app-shell`），使浏览器端（`web/`）与桌面端（`desktop/`）的线上界面与设计稿一致。

产出形态是**生产代码变更**，不是新的原型。

覆盖范围：

- 设计令牌（颜色、间距、字号、圆角、阴影、动效、层级），浅色与深色双主题
- 共享组件皮肤（按钮、表单、下拉、表格、徽标、状态、卡片、面板、标签页、弹层、空态）
- 应用壳层结构（一级导航由顶部横排改为左侧分组侧栏）
- 页面级布局与信息结构（工作台、项目、工作项列表与详情、资料库、消息中心、搜索、个人中心、系统管理）

明确不做：

- 不改 `api/` 的 Rust 业务逻辑、接口契约与数据模型
- 不重设计「时间管理」页面内容（`/web/time-management`），沿用现状；仅调整其在导航中的位置
- 不改动 `frontend/packages/app-core` 的路由词表与 `api-client` 的接口封装
- 不引入新的前端框架或运行时依赖（维持 React 19 + Vite）

### 关键约束（决定了本特性的实施形态）

1. **Web 与 Desktop 共用同一套前端包**。`desktop/src/renderer/app.jsx` 渲染的是 `SharedApp`，两侧都 import `frontend-ui/styles.css` 与 `frontend-app-shell/application.css`。
   任何 UI 改动**同时作用于两端**，无法只改一端，因此回归面天然翻倍。
2. **Parity 视觉合同硬编码了四项结构**：`tokens.topbarHeight='58px'`、`breakpoints=[1280,1100,980,920,900,860,760,620]`、
   `globalShell.regionOrder=['topbar','main']`、`viewports` 为 390/768/1280/1440。
   设计稿的左侧栏、60px 顶栏、375 起点断点与这四项**逐条冲突**，改动必须同步处理。
3. **Parity 校验是纯静态结构校验，不运行浏览器**。它只断言「登记的结构是否自洽且在白名单内」，
   **不验证 `stableAnchors` / `geometryAnchors` 里的选择器在真实 DOM 中仍然存在**。
   合同不构成视觉护栏，UI 大改需要另建护栏。
4. **Parity 清单是人工维护的静态数据**，无自动重写命令。视觉合同 31 页、体验清单 31 页 + 若干动作，
   两份文件按 `id` 双向闭合，任一侧页面条目变化必须同步另一侧，并保持 `evidence` 三类证据齐备。
5. **深色主题是既有能力不是新增能力**。`frontend/packages/ui/src/styles.css` 已有完整的
   `html[data-theme="dark"]` 令牌组，Desktop 启动即按宿主偏好设置 `data-theme`。
   设计稿目前只有浅色版本，暗色必须一并设计，否则桌面端深色模式会出现「新布局 + 旧暗色令牌」的割裂。

## 用户场景与验收

### US1：终端用户看到与设计稿一致的界面（优先级 P1）

- 优先级：P1
- Given：用户已登录元策，使用浏览器或桌面客户端
- When：浏览工作台、项目、工作项列表与详情、消息、系统管理等页面
- Then：界面布局、密度、色彩、状态表达与 `ui-v3/` 设计稿一致；两端表现相同
- 关键失败或边界场景：桌面端处于深色模式时，不能出现浅色布局配深色令牌的不一致

### US2：维护者改动 UI 时有可依赖的护栏（优先级 P1）

- 优先级：P1
- Given：维护者修改了组件样式或页面 DOM 结构
- When：运行 `make frontend-check` 与视觉回归
- Then：结构性破坏（选择器失效、关键区域消失、布局越界）能被自动发现，而不是靠人工肉眼比对
- 关键失败或边界场景：parity 合同登记的锚点在 DOM 中被删除后，现有校验不能发现

### US3：设计稿与生产实现不脱节（优先级 P2）

- 优先级：P2
- Given：设计稿在 `ui-v3/` 中调整了令牌或组件规格
- When：维护者把调整同步到生产实现
- Then：不存在两份需要人工同步的令牌定义，改动只有一处来源
- 关键失败或边界场景：设计稿令牌与生产令牌各自演化，出现「原型好看但线上不是」

### US4：Parity 合同在 UI 变更后仍然有意义（优先级 P2）

- 优先级：P2
- Given：UI 变更导致页面结构、锚点或响应式行为变化
- When：同步更新视觉合同与体验清单
- Then：合同登记的锚点、几何与响应式期望与真实实现一致，且两份清单保持双向闭合
- 关键失败或边界场景：只改视觉合同不改体验清单，或反过来

## 功能要求

- FR-001：设计令牌必须只有一处来源。生产实现与 `ui-v3/` 设计稿引用同一份令牌定义，不得各自维护。
- FR-002：必须提供浅色与深色两套完整令牌；深色主题下的正文对比度不低于 4.5:1。
- FR-003：共享组件必须达到设计稿的视觉规格：按钮、表单、下拉、表格、徽标、状态、卡片、面板、标签页、弹层、空态。
  允许复用既有组件实现（例如已有自定义下拉组件仅需换皮），但最终表现须与设计稿一致。
- FR-004：不得残留由浏览器绘制的原生控件（下拉、日期、搜索清除按钮等）；图标必须为 SVG，不得使用 emoji。
- FR-005：一级导航必须改为左侧分组侧栏，含分组标签、活动态指示与当前项目切换入口；「时间管理」作为常规导航项位于侧栏内，
  并显式标注其沿用现有实现。
- FR-006：工作台、项目列表、工作项列表、工作项详情、资料库、消息中心、全局搜索、个人中心、系统管理各子页，
  必须实现设计稿的信息结构与布局。
- FR-007：状态语义不得仅由颜色承载，必须同时具备文字或图形标识。
- FR-008：必须适配设计稿声明的视口宽度集合，且宽表由横向滚动容器承载，不得撑破布局。
- FR-009：全部可交互元素必须键盘可达且焦点可见，tab 顺序与视觉顺序一致。
- FR-010：必须响应 `prefers-reduced-motion`。
- FR-011：视觉合同与体验清单必须在 UI 变更后同步更新，保持双向闭合；视口、断点、壳层区域顺序、顶栏高度等硬编码值必须与实现一致。
- FR-012：必须建立可自动执行的视觉回归手段，能够发现选择器失效、关键区域缺失与布局越界。
- FR-013：`frontend/parity/legacy-source-inventory.json` 必须与 `api/src/web/router.rs` 与 `api/templates/web` 的真实内容保持一致；
  若本特性未改动 Rust 路由与 Askama 模板，则该文件不需变更。
- FR-014：变更不得影响附件、富文本、评论、时间分配甘特图等既有能力的外观以外行为；时间管理页面内容不得改动。
- FR-015：文档与设计决策必须同步更新，包括 `ui-v3/DESIGN-NOTES.md` 与本特性的任务记录。

## 成功标准

- SC-001：浏览器端与桌面端在设计稿声明的全部视口宽度下，无横向溢出、无元素重叠、无未捕获运行时错误。
- SC-002：视觉回归在每次 UI 变更后自动执行；人为删除一个合同登记的锚点后，回归必须失败。
- SC-003：`make frontend-check` 全部通过；parity 的 19 项相关校验保持通过，且合同登记的锚点在真实 DOM 中全部可解析。
- SC-004：浅色与深色主题下，正文与承载面的对比度均不低于 4.5:1。
- SC-005：设计令牌只有一处来源；设计稿与生产实现的令牌值一致。
- SC-006：两端（浏览器、桌面）表现一致，不存在只在一端生效的样式。
- SC-007：每个阶段可独立验证与回滚，出现问题可退回上一阶段而不留下半成品状态。

## 风险与验证要求

主要风险：

1. **两端同源导致的回归面翻倍**。对策：每个阶段必须同时在浏览器端与桌面端验证；桌面端的深色模式必须单独走查。
2. **Parity 合同与实现脱节**。现有校验不验证锚点存在性，是已知盲区。
   对策：FR-012 的视觉回归必须覆盖「合同登记的锚点在 DOM 中存在」这一条，把盲区补上。
3. **一次性全量回迁导致合同被打散**。31 页 × 多字段人工同步，失误概率高且难以定位。
   对策：按阶段推进，结构改造逐页进行，每页独立提交、独立验证、独立更新合同条目。
4. **设计稿本身尚未定稿**（暗色主题缺失）。对策：暗色主题与阶段划分绑定，未定稿部分不进入回迁。
5. **破坏既有可用性**。富文本、附件预览、评论、时间分配甘特图均为高交互密度组件。
   对策：这些组件本次只做皮肤调整不改行为，并单独走查。

验证层级：

- 既有：`npm --prefix frontend run check`（含 parity 19 项）、`npm --prefix web run check`、`npm --prefix web run test:e2e`
- 新增：视觉回归（截图与锚点断言），纳入 `make frontend-check`
- 真实运行：浏览器端与桌面端各一轮，逐视口截图比对
- 人工复核：设计稿与生产界面逐页并排比对，结论写入 `docs/reviews/`

需确认：`make frontend-check` 的 desktop 段当前因本机 `desktop/node_modules/typescript` 缺失而无法执行，
需补齐依赖后单独复核；该问题与本特性无关但影响验收完整性。

## 已决事项

- 阶段边界与每阶段的验收方式见 `plan.md`。**「壳层改造」（P3）与「页面改造」（P4）分开执行**：
  parity 合同 31 页需逐页手改并保持双向闭合，合并会让变更面一次性扩大到 31 页，失去逐页验证与逐页回滚的能力；
  分开后每页自成「实现 → 验证 → 提交」闭环。
- Parity 合同的 `viewports` 起点（390）与设计稿的 375 断点**分层处理，不强行统一为单一数字**：
  - 验收视口保持 `390 / 768 / 1280 / 1440` 不变。合同 schema 把 `viewports` 固定为 4 项，
    替换 390 会丢掉 iPhone 12/13/14 的真机覆盖，且 375 并不是「更正确的设备宽度」。
  - 设计侧最小支持宽度定为 **375**，作为 e2e 的额外窄屏档（不占合同的 4 档名额），
    并在 P4 逐页同步 `responsiveExpectations.mobile` 时明确覆盖 375–389 区间。
  - 依据：两者的差异来自设备宽度约定，不是设计意图；验收视口回答「在哪些宽度比对」，
    断点回答「布局在多窄时降级」，本可以并存。
